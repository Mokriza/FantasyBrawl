# ИИ-противник

Код — в `src/ai/`. Зависит только от `core`. ИИ — это обычный «игрок», который получает `BattleState` и возвращает `Action`. Он не имеет доступа ни к чему, чего нет у человека, кроме скорости перебора.

## Интерфейс

```ts
interface BattleAi {
  chooseActions(state: BattleState, content: ContentRegistry, rng: RngState): { actions: Action[]; rng: RngState };
}
interface DraftAi {
  choosePick(draft: DraftState, content: ContentRegistry, rng: RngState): { heroId: HeroId; rng: RngState };
}
```

- ИИ возвращает **план на весь ход** — последовательность действий. Интерфейс применяет их по одному с анимацией.
- ИИ использует **свой** `RngState` для шума, а не состояние боя. Иначе решения ИИ сдвигают криты, и детерминизм матча ломается при смене сложности.
- Перед применением каждого действия интерфейс проверяет, что оно всё ещё в `legalActions`. Если нет (что-то поменялось из-за триггера) — перезапрашивает ИИ с текущего состояния.

## Алгоритм боя

```
для каждого плана P из generatePlans(state):
    s' = применить P к копии state через applyAction
    score = evaluate(s', side) + noise(profile)
выбрать P с максимальным score
```

### Генерация планов

Полный перебор всех последовательностей на 4 AP даёт слишком много вариантов. Используем структуру «перемещение → действие → перемещение → действие»:

1. `move?` — на любой достижимый гекс или остаться.
2. `ability?` — любая доступная способность на любую допустимую цель с этой позиции.
3. Если AP остались — ещё раз шаги 1–2 с новой позиции.
4. `endTurn`.

Отсечения, чтобы уложиться в бюджет:

- Перемещения второго уровня — только на гексы в пределах 2 от текущей позиции.
- Для способностей с зоной — только целевые гексы, где зона задевает хотя бы одного героя.
- Способности «про землю» (`teleport`, `terrain`, `summon`) никого не задевают, поэтому для них берутся по 3 допустимых гекса с каждого края: ближайшие к врагу (капкан, бес, стена на пути) и самые далёкие от него (побег телепортом).
- Жёсткий лимит: `config.ai.maxPlans` (5000). При превышении — берутся первые по эвристике «план с атакой раньше плана без атаки».
- Оценка ожидаемого урона в плане делается через `applyAction` с **замороженными бросками**: `applyAction(state, action, content, { deterministic: true })` даёт разброс 1.0 и выключенный крит. ИИ не должен «подглядывать» результат реального броска и не тратит боевой `rng`.
- Крит именно **выключен**, а не взят как матожидание: матожидание даёт дробный урон, а `code-style.md` требует, чтобы все игровые значения после округления были целыми. Цена решения — ИИ равномерно недооценивает крит-билды; это лучше, чем дробные значения в ядре.

### Оценочная функция

Оценивает итоговое состояние с точки зрения стороны ИИ. Веса — в `config.ai.weights`, стартовые значения:

| Слагаемое | Вес | Как считать |
|---|---|---|
| `damageDealt` | 1.0 | Сумма снятого врагам здоровья за план |
| `kill` | 80 | За каждого убитого врага |
| `overkill` | −0.8 | За каждую единицу урона сверх оставшегося здоровья |
| `hpLost` | −1.2 | Собственное потерянное здоровье (самоурон, Яма) |
| `healing` | 0.9 | Эффективное лечение, не больше недостающего |
| `controlTurns` | 25 / 12 | Ход оглушения / немоты на враге |
| `threat` | −0.4 | Ожидаемый урон, который враги смогут нанести по гексу героя в свой следующий ход |
| `distanceToTarget` | −2.5 | За каждый гекс сверх дальности базовой атаки до ближайшей цели |
| `highGround` | 8 | Герой стоит на возвышенности |
| `ultimateSaved` | 5 | Способность тира IV осталась неиспользованной |
| `focusBonus` | 10 | Урон по цели, которую союзники ИИ уже ранили ниже 60% |
| `summonDamage` | 0.6 | Ожидаемый урон своих призывов: сила × `k` × оставшиеся ходы; чужих — со знаком минус |
| `trapNearEnemy` | 8 | За каждый свой капкан в пределах `apPerTurn` гексов от врага |

Отложенный урон («Метеор») оценка пока не видит: план с ним выглядит как трата AP впустую, поэтому ИИ применяет его редко.

`threat` — самое дорогое слагаемое. Считать его упрощённо: для каждого живого врага — максимальный урон его доступных атак по этому гексу, если гекс в его досягаемости (перемещение + дальность). Линию видимости в `threat` не учитывать.

### Профили сложности

Из `config.ai.profiles`:

| Профиль | `noise` | `threat` | Тир IV | `lookahead` |
|---|---|---|---|---|
| `novice` | 0.40 | выключен | запрещён | 0 |
| `normal` | 0.15 | включён | разрешён | 0 |
| `veteran` | 0.05 | включён | разрешён | 1 |
| `nightmare` | 0 | включён | разрешён | 2 |

- `noise` — множитель шума: `score × (1 + rng.float(-noise, noise))`. Шум к оценке, а не случайный выбор плана.
- `lookahead: 1` — для топ-10 планов прогнать лучший ответ следующего по ATB врага и оценивать состояние после него. `lookahead: 2` — то же на два хода вглубь, только для топ-5.
- Начинать с `normal`. Остальные профили — после того как `normal` не делает явных глупостей.

## Драфт

Простая версия, с которой начинаем:

```
score(hero) = (powerEstimate(hero) + roleBonus(hero, myPicks)) × (1 + шум)
```

Реализовано в `src/ai/draft.ts` (`choosePick`), веса — `config.ai.draft`.

- `powerEstimate` — обе части в очках бюджета, делённых на бюджет, чтобы веса сравнивали одинаковое:
  - характеристики: очки каждой характеристики × её вес для класса (те же `generation.statWeights`, что у генератора, делённые на вес главной: главная 1, второстепенные 0.75, остальные 0.25) — очко в «чужую» характеристику стоит меньше;
  - способности: их цена в бюджете — тир уже говорит, чего способность стоит.
- `roleBonus` — `+missingRoleBonus` (0.15), если роли героя ещё нет в команде; `−duplicateRolePenalty` (0.1), если эта роль уже взята дважды. На шкале, где сила героя около 0.7–0.8, это те же пропорции, что `+30 / −20` в исходном наброске.
- Шум умножает оценку (`ai.draft.noise`, 0.05), как в бою: слабый пик — разумный, а не случайный. Поток случайности — свой, отдельный от потока забега.
- Сильная версия — учёт того, что уже взял игрок, и контрпики — пока не делается.

### Расстановка

`src/ai/placement.ts` (`choosePlacement`) — эвристика, не поиск:

- первыми ставятся танки и бойцы ближнего боя, чтобы занять передний столбец;
- ближние — в столбец стартовой зоны, ближний к врагу, дальние и поддержка — в задний;
- штраф за удаление от среднего ряда, дальним — штраф за соседство со своими (против площадных ударов);
- немного шума, чтобы расстановки не повторялись.

### Между матчами

- Замена героя в фазе усиления (этап 4) — та же функция, но с учётом, какого героя убираем: самого слабого по `powerEstimate`, если новый лучше хотя бы на 15%.
- Выбор перков: `src/ai/perks.ts` (`choosePerk`), жадно. Ценность перка — сумма ценностей его модификаторов для класса (характеристики — по тем же весам `generation.statWeights`, что у генератора; урон дороже для не-поддержки, лечение — только для поддержки, защита — для танков, дальность — для дальних), триггер стоит 0.5, перк на способность 0.7 и ставится на способность высшего тира с самым длинным кулдауном. Плюс шум `ai.draft.noise`. Выбор предметов — этап 4.
- Выбор награды: `chooseReward` там же. Пара «артефакт, герой» с наибольшим приростом: ценность нового артефакта для героя минус ценность того, что он несёт. Ценность — как у перка, по модификаторам, триггер 0.5. Плюс шум `ai.draft.noise`.
- Выбор открытий: `chooseUnlock` там же, жадно, с тем же шумом. Пассивка — по той же ценности модификаторов, что перк, триггер 0.5. Способность тира IV — сумма коэффициентов урона (× число ударов) и лечения; поддержке лечение ценнее урона, остальным наоборот; любой другой атом — 0.4.

## Как понять, что ИИ плохой

Не на глаз. Через `sim`:

- Турнир профилей: `veteran` должен обыгрывать `normal` в 65–80% матчей, `normal` — `novice` в 75–90%. Если разница меньше — оценочная функция не различает хорошие и плохие ходы.
- Счётчик «бессмысленных ходов»: план без урона, лечения, статусов и с увеличением расстояния до ближайшей цели. На `normal` — меньше 5% ходов.
- Перебор весов делать турнирами: меняем один вес, 2000 матчей против текущей версии, оставляем изменение, если винрейт вырос больше чем на 3 процентных пункта.

## Производительность

- Цель: решение за ход < 200 мс на профиле `normal` в браузере.
- Если медленно — сначала профилировать, потом резать планы. Не переходить на Web Worker, пока не упрёмся в 500 мс.
- Не оптимизировать `applyAction` под ИИ ценой читаемости. Лучше меньше планов.
