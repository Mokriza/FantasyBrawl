# Стиль кода

Цель — код, который пользователь (Java-разработчик, новичок в TypeScript и геймдеве) может читать без подготовки, и который потом переносится на C# без переписывания логики.

## TypeScript

- `strict: true`, плюс `noUncheckedIndexedAccess: true` и `exactOptionalPropertyTypes: true`.
- Никаких `any`. Если тип неизвестен — `unknown` и сужение. `as` — только с комментарием, почему это безопасно.
- Никаких `!` (non-null assertion) в `core`. Отсутствие значения обрабатывается явно.
- `interface` для форм данных, `type` для объединений. Дискриминированные объединения с полем `type` — основной способ описывать варианты (действия, события, эффекты).
- `switch` по дискриминанту всегда заканчивается проверкой исчерпанности:

```ts
function assertNever(x: never): never { throw new Error(`Unhandled: ${JSON.stringify(x)}`); }
```

- `enum` не использовать. Строковые литералы в объединениях.
- Брендированные идентификаторы для ключевых сущностей: `type HeroId = string & { readonly __brand: 'HeroId' }`. Предотвращают перепутывание `heroId` и `abilityId`.

## Функции и данные в `core`

- Функции, а не классы. Классы в `core` запрещены (кроме ошибок `extends Error`).
- Функции короткие: если больше 40 строк — вероятно, делает две вещи.
- Чистота: результат зависит только от аргументов, аргументы не мутируются.
- Нет глобального изменяемого состояния. Нет синглтонов. Реестр контента передаётся параметром.
- Нет генераторов, прокси, декораторов, сложных условных и шаблонных типов. Это не переносится на C#.
- Числа: только `number`. Все игровые значения — целые после округления. Дробные — только промежуточные вычисления внутри формул.

## Именование

| Что | Стиль | Пример |
|---|---|---|
| Файлы | `camelCase.ts` | `legalActions.ts` |
| Функции, переменные | `camelCase` | `applyDamage`, `apLeft` |
| Типы, интерфейсы | `PascalCase` | `BattleState`, `DamageEvent` |
| Константы модуля | `UPPER_SNAKE` | `DIRECTIONS` |
| Идентификаторы контента | `snake_case` | `warrior_cleave` |
| React-компоненты | `PascalCase.tsx` | `AbilityBar.tsx` |

Термины игры в коде — одинаковые везде: `hero` (не `unit`, `character`), `ability` (не `skill`, `spell`), `side` (не `team`, `player`), `status` (не `buff`, `effect` — `effect` занят атомами), `ap`, `atb`.

## Ошибки

- `core` бросает исключение на недопустимое действие и на невалидный контент. Это ошибки программиста, не игрока.
- Ожидаемые отказы (нет AP, кулдаун, нет обзора) — не исключения, а причина в результате проверки: `{ ok: false, reason: 'no_los' }`. `reason` — строковый литерал, текст для игрока подбирает `ui`.
- Никаких `try/catch`, проглатывающих ошибки. Поймал — либо обработал осмысленно, либо пробросил.

## Комментарии

- На английском.
- Объяснять **почему**, а не что. `// barrier absorbs before defense, otherwise it scales with target armor` — хорошо. `// subtract barrier` — не нужно.
- Каждое правило, отличающееся от «очевидного», ссылается на раздел спецификации: `// see game-rules.md §7, repeat-CC rule`.
- `TODO` только с пояснением, что именно и почему не сейчас.

## Зависимости

Уже согласованы: `react`, `react-dom`, `pixi.js`, `zod`, `vite`, `vitest`, `tsx`, `typescript`, `eslint`, `prettier`, плюс стор (см. `ui-and-rendering.md`). Любая новая зависимость — **только после вопроса пользователю**, с объяснением, зачем она нужна и почему нельзя без неё. В `core` зависимостей, кроме `zod`, быть не должно.

## Форматирование

Prettier с настройками по умолчанию, ширина строки 100, одинарные кавычки. Не спорить со стилем вручную — запускать `prettier --write`.

## Коммиты

- Conventional commits: `feat(core): add poison status`, `fix(ai): threat ignores dead heroes`, `balance: lower fireball k to 1.2`, `docs: update game-rules §6`.
- Отдельный тип `balance:` для изменений чисел в контенте и конфиге — чтобы их было легко найти в истории.
- Один коммит — одно логическое изменение. Правка правил и правка баланса — разные коммиты.
