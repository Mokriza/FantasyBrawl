# Тесты и симуляция

Тесты в `core` обязательны. Тесты в `ui` — по желанию. Симуляция — это инструмент баланса, а не тест, но она тоже должна проходить без ошибок.

## Что тестируем и как

| Уровень | Где | Что проверяет |
|---|---|---|
| Юнит | `core/**/__tests__/*.test.ts` | Одна функция: формула, гексовая геометрия, тик статуса |
| Сценарий | `core/battle/__tests__/scenarios/` | Одно действие на заданном поле, проверка событий и состояния |
| Способность | `core/battle/__tests__/abilities/` | По одному тесту на каждую способность из контента |
| Инвариант | `core/battle/__tests__/invariants.test.ts` | Свойства, которые должны выполняться в любом матче |
| Контент | `npm run validate-content` | Схемы и правила пулов |
| Симуляция | `npm run sim` | Баланс, длина матчей, отсутствие падений |

## Сценарные тесты

Сценарий строится билдером, а не руками:

```ts
const s = scenario()
  .seed(42)
  .hero('w', { cls: 'warrior', side: 'A', at: [2, 3], attack: 20 })
  .hero('m', { cls: 'mage',    side: 'B', at: [3, 3], hp: 100, armor: 0 })
  .obstacle('rock', [4, 3])
  .active('w', { ap: 4 })
  .build();

const { state, events } = applyAction(s, { type: 'ability', heroId: 'w', abilityId: 'warrior_cleave', target: hex(3, 3) }, content);

expect(events).toContainEqual(expect.objectContaining({ type: 'damaged', targetId: 'm' }));
expect(state.heroes.m.hp).toBe(74); // закреплено для seed 42
```

- Билдер `scenario()` живёт в `core/testing/` и экспортируется только для тестов.
- Для проверки точного урона фиксируем сид. Если нужна проверка формулы без случайности — билдер умеет `.noVariance()`, подменяя разброс на 1.0 и крит на выключенный.
- Проверяем **события**, а не только итоговое состояние. События — это контракт с интерфейсом.

## Инварианты

Прогоняются на 200 случайных матчах ИИ против ИИ с разными сидами. Любое нарушение — падение теста с выводом сида для воспроизведения.

1. `applyAction` не мутирует входное состояние (глубокое сравнение с замороженной копией).
2. Каждое действие из `legalActions` применяется без исключения.
3. После каждого действия: `0 <= hp <= maxHp`, `apLeft >= 0`, `cooldown >= 0`, никакие два героя не стоят на одном гексе.
4. Матч всегда заканчивается не позже `maxRounds`.
5. Состояние сериализуется: `JSON.parse(JSON.stringify(s))` эквивалентно `s`.
6. **Детерминизм:** один сид + одна последовательность действий → побитово одинаковое финальное состояние при двух прогонах.

## Детерминизм

- Сид матча и сид ИИ задаются явно везде: в тестах, в симуляции, в игре. В игре сид генерируется один раз при старте забега и показывается в интерфейсе — чтобы баг можно было воспроизвести.
- Любой отчёт об ошибке в симуляции содержит сид и номер матча.
- Если тест с фиксированным сидом начал давать другое число после изменения, **не** обновляй ожидание молча. Сначала объясни, почему число изменилось. Допустимые причины: изменена формула, изменён порядок бросков, изменён контент. Если причина неизвестна — это баг.

## Симуляция баланса

```bash
npm run sim -- --matches 10000 --seed 1 --profile normal --out sim-report.json
npm run sim -- --mode draft --runs 200 --seed 1   # полные забеги: драфт, расстановка, серия
npm run sim -- --mode draft --runs 50 --shards 16 --seed 1 --out report.json   # то же в 16 процессах
npm run sim -- --mode tournament --a veteran --b normal --matches 2000
```

`sim` запускается через `tsx` в Node. Никакого браузера. Режим `tournament` (этап 5): `--a` против `--b` на ростерах `teams.json`, профили меняются сторонами через матч, печатает долю побед `--a`.

Полный забег ИИ против ИИ — `src/sim/series.ts` (`playRun`). Он же используется в `src/sim/__tests__/series.test.ts`: несколько забегов целиком, проверка, что серия кончается ровно на трёх победах за 3–5 матчей, что в каждом бою по три героя на сторону нужного уровня (замены между матчами меняют, кто они) и что забег детерминирован по сиду. Забег — это до пяти боёв, поэтому забегов в тесте немного; инварианты самого боя по-прежнему проверяются на 200 матчах.

### Отчёт

Отчёт — JSON плюс текстовая сводка в консоль. Счётчики собирает `src/sim/report.ts`: они складываются, поэтому `--shards N` делит забеги на N процессов с разными блоками сидов и сливает итог точно. Винрейты классов, ролей, рас, пассивок, артефактов и перков считаются по героям в матчах: герой, сыгравший матч, — одно появление, победа, если его сторона взяла матч.

Метрики:

| Метрика | Целевое значение | Что значит отклонение |
|---|---|---|
| Средняя длина матча | 8–12 раундов | Больше — мало урона. Меньше — слишком много бурста |
| Доля матчей по лимиту раундов | < 3% | Больше — танки непробиваемы |
| Винрейт по классам | 45–55% каждый | Разброс > 10 п.п. — класс сломан |
| Винрейт по ролям | 45–55% | Особенно следить за `ranged`: на маленьком поле дальники бьют с первого хода |
| Винрейт первого пика в драфте | 48–52% | Нужна или не нужна компенсация |
| Отстающий при 0–2 берёт 3-й матч | ≥ 35% (GDD) | Меньше — догонялку (`run.catchUp`) усиливать |
| Доля фаз усиления с заменой героя | для сведения | Около нуля — замена бесполезна или `ai.draft.swapMargin` слишком строг |
| Доля способностей, применённых хотя бы раз | > 60% для каждой | Меньше — способность слишком дорогая или бесполезная |
| Доля ходов, потерянных на контроль | < 12% | Больше — контроль душит игру |
| Винрейт стороны после 0–2 в серии | > 35% | Меньше — догонялка слишком слабая |

### Правила работы с симуляцией

- Любое изменение чисел баланса сопровождается прогоном `sim` до и после, с одинаковым сидом. В ответе пользователю — дельта ключевых метрик.
- Не подгонять числа под целевые значения автоматически без согласования. Симуляция показывает проблему; решение о балансе принимает пользователь.
- Симуляция на 10 000 матчей должна укладываться в пару минут. Если нет — сначала профилировать ИИ, потом ядро.

## Чего не тестируем

- Интерфейс снимками. Он будет меняться постоянно.
- Pixi-отрисовку.
- Тексты описаний (их проверяет `validate-content`).
