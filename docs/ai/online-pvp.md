# Онлайн PvP через лобби

Этап 5б. Сделано: часть 1 (`src/net`), часть 2 (`src/server`). В работе: клиент и размещение.

## Решения пользователя

- Игрок против игрока через лобби.
- Транспорт — **свой сервер Node + WebSocket**. Сервер запускает тот же `core` и проверяет каждое действие, как требуют GDD и `architecture.md`. Клиенту не доверяем.
- Реализация — после этапа 5.
- Таймеры: пик в драфте 60 с (GDD), расстановка 30 с на героя, фаза усиления 120 с, ход в бою 30 с. По истечении сервер сам делает ход за игрока. Числа — `config.online`.
- Выборы соперника в фазе усиления видны сразу, как в игре с ИИ.
- В первой версии — лобби по коду, забег, переподключение и чат комнаты. Реванша и зрителей нет.
- Хостинг — Render.

## Как это устроено

```
GitHub Pages (клиент, как сейчас)  ── wss:// ──  сервер Node (src/server)
        │                                             │
   ui + core (локально проигрывает               core (единственный судья:
   присланные действия → события)                applyRunAction / applyAction)
```

- **Сервер авторитетен.** Клиент шлёт только намерение — `RunAction` или `Action`. Сервер проверяет, что отправитель — нужная сторона и что действие законно (`legalActions` для боя, фаза и сторона — для забега). Затем применяет его и рассылает обоим.
- **Синхронизация — список действий.** Ядро детерминировано и сидировано, поэтому клиент, получив от сервера сид и поток принятых действий, сам воспроизводит то же состояние и события для анимации. Так уже устроен реплей в `invariants.test.ts`. Урон клиент не считает «от себя»: он лишь повторяет действия, одобренные сервером.
- **Проверка версии.** При входе клиент сообщает хеш контента и версию сборки. Если они не совпадают с серверными, в комнату не пускаем: при разном контенте детерминизм ломается.
- **Случайность.** Сид забега бросает сервер (`crypto`). Это вне `core`, так что правило «никакого `Math.random` в core» не нарушается.
- **Скрытой информации в правилах нет** (GDD), поэтому оба клиента получают одно и то же.

## Лобби

- «Создать игру» → сервер создаёт комнату с кодом из 5 символов (без похожих букв: 0/O, 1/I). Создатель видит код и ждёт.
- «Войти по коду» → второй игрок занимает второе место. Третьему — «комната заполнена».
- Оба нажимают «Готов» → старт. Кто драфтует первым, решает бросок сервера, как сейчас `createRun`.
- Имена игроков без аккаунтов: ник из поля ввода, хранится в `localStorage`.
- Публичного списка комнат на первой версии нет, только код **[предложение]**.

## Что меняется в ядре

Немного, и всё это полезно и для игры против ИИ:

1. **Готовность в фазе усиления — у каждой стороны своя (сделано, часть 1).** `readyUpgrade { side }` и `unreadyUpgrade { side }`, переход к расстановке — когда готовы обе. ИИ сразу ставит «готов».
2. **Кто может отправить действие.** Функция `actorOf(run, action): Side | null`: сторона, которой принадлежит действие. Боевое действие принадлежит стороне активного героя. Сервер сверяет её с местом отправителя.
3. **`RunState.playerSide`** — понятие локальной игры. На сервере не используется, клиенту приходит «вы — сторона A/B».
4. **Таймеры** остаются в интерфейсе и на сервере, не в `core`. Истечение времени — обычное действие: `autoPick` уже есть, для боя добавится `endTurn` от имени сервера.

## Протокол (JSON, схемы Zod в `src/net/`)

| Клиент → сервер | Сервер → клиент |
|---|---|
| `hello { version, contentHash, name }` | `welcome { playerId, token }` |
| `createRoom` | `room { code, seats, ready }` |
| `joinRoom { code }` | `started { seed, you: Side, names }` |
| `ready` / `unready` | `applied { seq, action }` — принятое действие |
| `act { seq, action }` — `RunAction` или `Action` | `rejected { seq, reason }` |
| `resume { token }` | `snapshot { seed, actions[] }` — для переподключения |
| `leave` | `opponentLeft`, `opponentBack`, `ended { winner, reason }` |

- `seq` — номер действия в логе комнаты. Он отсекает дубли и гонки: действие, отправленное на устаревшее состояние, отклоняется.
- Сервер держит лог действий комнаты. Состояние восстанавливается прогоном лога.

## Таймеры и обрывы связи

- Пик в драфте — 60 с (GDD), по истечении сервер делает `autoPick`.
- Расстановка — 30 с на героя, по истечении герой встаёт на первый свободный гекс зоны. Фаза усиления — 120 с на всю фазу (выборы внутри часы не перезапускают, чтобы нельзя было тянуть время), по истечении сервер делает оставшиеся выборы первыми вариантами и ставит «готов». Ход в бою — 30 с, по истечении конец хода. После матча — 20 с на «Далее» (`continueSeconds`), потом следующий матч начинается сам. Часы — `src/server/auto.ts`.
- Обрыв связи: место держится 2 минуты, и соперник видит «ждём соперника». Переподключение по `token` из `localStorage` → `snapshot` → клиент прогоняет лог. Не вернулся — техническое поражение в забеге.

## Размещение

- Клиент остаётся на GitHub Pages. Адрес сервера — `VITE_SERVER_URL` при сборке. Пустой адрес — пункт «Игра по сети» скрыт, и сайт работает как сейчас.
- Сервер — бесплатный Node-хостинг с WebSocket (Render или Fly.io). На бесплатном Render сервис засыпает без трафика, первое подключение ждёт 30–60 с — клиент показывает «сервер просыпается».
- Проверка `Origin` (только наш сайт и localhost), ограничение частоты сообщений, лимит комнат.
- Деплой сервера — отдельный workflow в GitHub Actions. Секреты хостинга хранит пользователь в настройках репозитория.

## Структура

```
src/
  net/      протокол: типы и схемы Zod сообщений. Зависит от core
  server/   Node: комнаты, лог действий, таймеры, ws. Зависит от core и net
  ui/net/   клиент: подключение, лобби, отправка действий, прогон принятых
```

ESLint расширяется: `server` не импортирует `ui`, `net` не импортирует ни `ui`, ни `server`.

## Части реализации

1. **Ядро:** `readyUpgrade`/`unready` по сторонам, `actorOf`, тесты. Игра против ИИ продолжает работать.
2. **Протокол и сервер:** комнаты, коды, лог, проверка действий, таймеры. Тесты на сокетах в памяти: два бота из `ai/` играют забег через сервер, итог совпадает с прогоном без сети.
3. **Клиент:** экран «Игра по сети» (создать / войти по коду / готов), сетевой режим стора. Вместо ответов ИИ ждём `applied` от сервера.
4. **Обрывы и переподключение, таймеры в интерфейсе.**
5. **Размещение:** хостинг, workflow, переменная `VITE_SERVER_URL`, README.
